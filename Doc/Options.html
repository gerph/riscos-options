Introduction and Overview

Usage of the Choices: structure has historically been disorganised, with each application author selecting their own particular way of storing options. Many applications fail to use the correct way of accessing the Choices: structure, and some still use files kept in their own private directory structure.

This suggests the need for a central module to maintain configuration options for applications. The files it controls are textual, so as to allow the user to fix problems by hand if necessary.

This module provides:

  • A means of reading options files, either from Choices: or an arbitrary location
  • A means of writing options files, to the correct part of Choices: or to the original location
  • A means of collating related items within a file into 'groups'

Technical details

User interface

There is no user interface provided by this module.

Programmer interface

The programmer interface is incomplete and may change without notice.

Data formats

Options files are standard RISC OS text files. Any whitespace (space or tab) at the beginning or end of a line is ignored. Any line where the first non-whitespace character is # is a comment line and is ignored, as is any line consisting only of whitespace.

The file consists of a series of groups, delimited by group name specifiers. A group name specifier starts with [, followed by the name (which may contain spaces), followed by ].

The groups themselves are in one of two formats (although further formats may be added in future):

  • The list format is a simple list of newline-terminated strings.
  • The options format consists of tag, value pairs in the form <spaces>tag name<spaces>:<spaces>value<spaces>, where <spaces> is zero or more spaces or tabs.

Items at the start of a file, before any group is declared, are deemed to be in the group $. Group names are case insensitive, as are tag entries. 

An example options file for an application called "widget"



# choices file for widget

[auto load]
# a list of files to load when starting widget
ADFS::4.$.afile
ADFS::4.$.somedir.anotherfile
ADFS::4.$.thingy

[misc options]
somevalue    : 42
window width : 332
auto open    : Yes

When a group is read with SWI Options_ReadGroup or written with SWI Options_WriteGroup, its content is passed as a block of memory in one of two layouts, matching the group format.

For an options group, the block holds a series of tag/value pointer pairs, terminated by a null pair:

OffsetSizeNameContents
04tagPointer to tag 0
44valuePointer to value 0, or NULL if no value is set (for example in list groups)
xRepeated tag/value pointer pairs
x4tag0
x+44value0

For a list format group, the buffer is filled with a series of null-terminated strings immediately following one another.

This module allocates the Options_ SWI chunk at &52F80.

Options_OpenFileSWI &52F80
Open an options file

Bit(s)NameMeaning
0-1Method of accessing file
ValueMeaning
0R1 contains an absolute filename
1R1 contains the leafname, R2 contains the application name, and R3 contains another directory name to use if Choices: is not present, or the Choices: file is not present
2-3Reserved
2-31Reserved, must be zero
R1=Pointer to filename, or leafname
R2=Pointer to application name
R3=Pointer to directory to use
R0=Opaque options handle
Interrupts are undefined
Fast interrupts are undefined
Processor is in undefined mode
Not defined

This SWI is used to open a specific file, or a Choices: file, for access. When opening a specific file (type 0), only that file is written to and read from.

When opening a Choices: file (type 1), the file read comes from Choices:<application>.<leafname> if that is present, or if not, from <directory>.<leafname>. This provides compatibility for applications written for older systems. When writing, data is written to <Choices$Write>.<application>.<leafname> unless the Choices: structure is not present, in which case it is written to <directory>.<leafname>.

Testing scheme

Acceptance test

The options file parser must be capable of coping with very malformed files. Users, and programmers, will edit the files by hand and often get that wrong. At worst the program should fail to read a few options, but even in the worst cases the vast majority of the file should be able to be read.

The layout of option files must be preserved, as it will be laid out in such a way as to make it easier for the human reader. So, any whitespace must remain in the file after it is modified, as should any comments. If no changes are made to the options then the file written out should be identical to the file read in.

Transition to the Options system should be as painless as possible for both programmers and users.

Test strategy

The Options module should be tested by a number of programmers, in their own applications, as well as in some of the OS components.
